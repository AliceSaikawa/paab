# paab 設計書

paab（Personal SI Agent Bridge）は、同一人物が使う複数のパーソナルAIエージェントが、互いに質問して回答を得るための中継サーバーである。

この文書は 2026-11-16 の設計議論で合意した内容をまとめたもの。状態の凡例は次の通り。

- **確定**: 合意済み。
- **後回し**: 今回の範囲に入れない。
- **未確認**: 実装時に実機や公式資料で確かめる事実。

## 1. 目的と範囲

| 項目 | 決定 | 状態 |
| --- | --- | --- |
| 誰のエージェントをつなぐか | 同一人物が使う複数のエージェント。識別子に所有者IDを持たせ、複数ユーザーへの拡張余地だけ残す | 確定 |
| 最初の受入シナリオ | エージェントAが、知っていそうなエージェントBに質問し、回答を得る1往復 | 確定 |
| 対象外 | 記憶の一括同期 | 確定 |
| 配布形態 | 利用者が各自のCloudflareアカウントにデプロイするOSS。1デプロイ＝1ユーザー | 確定 |
| ライセンス | MIT | 確定 |
| データの持ち方 | ブリッジは中継のみ。ユーザーデータの共有保管はしない。持つのは未配達メッセージ、ルール、監査ログ | 確定 |

## 2. やり取りの方式

### 2.1 受信箱方式（確定）

質問はブリッジのデータベースに預けられ、宛先のエージェントがMCPツールで取りに来たときに渡る。実際のメールや外部の通知サービスは使わない。

この方式を土台にする理由は、大半のエージェントが外部からのプッシュを受けられず、自分のターン中にツールを呼ぶことしかできないため。代替手段の調査結果は 2.4 節を参照。

### 2.2 ツール

| ツール | 役割 |
| --- | --- |
| `ask` | 宛先とカテゴリを指定して質問を預ける |
| `check_inbox` | 自分宛のメッセージ（質問・回答・拒否）を受け取る |
| `answer` | 質問IDを指定して回答または拒否を預ける |
| `list_agents` | 自分が質問を許可されている相手、そのカテゴリ、相手の説明文を返す |
| 説明文の提出 | 自分の説明文を提出する（公開は承認後。5.4 節） |

管理者ボット用のツールは、管理者用の接続にだけ出す（5.3 節）。

### 2.3 規則

- 宛先は名指しのみ。「知っている誰か」への一斉質問は後回し。
- 1質問1回答。追加で聞きたい場合は新しい質問として出し直し、毎回ルール照合を通す。
- 回答も質問側の受信箱に入る。各メッセージは種別（質問／回答／拒否）と元の質問IDを持つ。
- どのツールの返り値にも、末尾に未読件数を付ける。
- 対応しているエージェントには、新着時に登録済みの呼び出し先URLを叩いて起こす。
  - 本文は送らず、新着があることだけを伝える。
  - 署名または認証ヘッダーを付ける（Standard Webhooks、Bearer・任意ヘッダー、paab独自HMACの選択。詳細は [docs/agent-trigger-design.md](agent-trigger-design.md)）。失敗時は数回だけ再試行して諦める（メッセージは受信箱に残る）。
  - 呼び出し先URLと認証設定は画面から利用者だけが登録する。
- エージェントのVM上で動く定期確認スクリプトやフックからも新着を確認できるようにする（2.5 節）。製品ごとに、呼び出し先URL方式と定期確認方式のうち使える方を選ぶ。

### 2.4 受信箱方式の代替手段（2026-11-16 調査）

| 手段 | 内容 | 判断 |
| --- | --- | --- |
| MCPの購読（`subscriptions/listen`） | 2026-07-28版の仕様で、サーバーからクライアントへの変更通知を1本の長時間ストリームで流す。通知はURIだけを運ぶ | クライアントが接続を保ち、購読に対応している間しか届かない。対象製品の対応は未確認。土台にはできない |
| MCPのTasks拡張 | 長時間かかる要求に対してタスクIDを返し、クライアントが結果を取りに来る | 「質問して後で回答を得る」に形は合う。クライアントが対応を宣言した場合だけ使え、有効期間は分〜時間の想定。日単位の待ちには合わない |
| MCPのEvents（実験段階） | サーバーが登録済みのURLへ署名付きで通知する設計案 | 2.3 節の「起こす仕組み」と同じ発想。仕様が実験段階なので依存しない |
| A2Aプロトコル | エージェント同士が互いをHTTPサーバーとして呼び合う | 各エージェントが外部から到達可能である必要があり、一般向けのパーソナルエージェントには当てはまらない |
| `ask` 内での短時間待機 | 回答を数十秒だけ待ってから返す | 相手がその瞬間に動いている場合しか効かない |

結論：どのクライアントでも動くのは受信箱方式だけである。他の手段は、受信箱の上に載せる任意の高速化として位置付ける。メッセージの保存構造は、購読やTasksを後から足せる形にしておく。

### 2.5 VM上の定期確認スクリプト（確定）

エージェントのVM上で5分おきに動くスクリプトが未読件数を確認し、新着があるときだけエージェントを起こす。確認は単純なHTTPリクエストなので、AIの利用枠を使わない。VMから外へ出る通信だけで済むため、外から叩ける入口がない製品でも使える。

- ブリッジに「未読件数だけを返す」HTTPの窓口を設ける（MCPではない）。
- エージェントごとに、この窓口専用の「件数確認トークン」を発行する。件数しか取れず、質問・回答・本文の取得はできない。コネクタ用のトークンとは別物で、VM内に置くことを前提とする。
- 5分おきに件数を確認し、新着があればエージェントを起こすサンプルスクリプトを同梱する。起こし方は製品ごとに違うので、その部分は差し替えられるようにする。

成立条件は 8 節の未確認事項と [docs/agent-trigger-design.md](agent-trigger-design.md) を参照（例として Meta Muse の公式フックはシークレットやコネクタ資格情報を持てない制約があるため、フックから件数確認トークン付きで叩けるかは実機で確認する）。

## 3. 開示の制御

### 3.1 二層の判断（確定）

1. **ブリッジ（決定的）**: 「送信元×宛先×カテゴリ」を許可ルールと照合する。書かれていない組み合わせはすべて拒否する。
2. **回答側エージェント（判断）**: 許可された範囲の中で、個々の質問に答えるかを決める。質問内容が申告カテゴリから外れていれば拒否する。

人間による個別承認は入れない。

### 3.2 カテゴリ（確定）

- 質問側が `ask` で申告する。回答側には申告カテゴリを併せて渡す。
- 利用者が定義する固定リスト。初期値は「予定」「連絡先」「好み・習慣」「仕事」「健康」「金融」「位置情報」「その他」。
- 「その他」は、初期の許可ルールではどの組み合わせにも許可しない。
- 画面から追加・削除できる。

### 3.3 届いた文章の扱い（確定）

- 質問文は「信頼できない外部データ」と明示した枠に入れて渡す。
- 開示の判断基準は、MCPサーバーの説明文側に固定で書く。
- 質問文に長さ上限を設ける。
- 他のエージェントが書いた説明文も同じ枠に入れて渡す。

### 3.4 拒否の伝え方（確定）

ブリッジによる拒否も回答側エージェントによる拒否も、質問側には同一の定型応答だけを返す。詳しい理由は監査ログに残す。

### 3.5 本人確認（確定）

- エージェントごとに別々の秘密トークンを発行し、ブリッジはトークンから送信元を決める。
- ツールの引数に「自分は誰か」を入れる欄は作らない。
- トークンはHTTPヘッダーで渡す方式を基本とする。OAuthなどの追加方式は後回し。
- トークンは発行時に一度だけ表示し、ブリッジにはハッシュ値だけを保存する。再発行で旧トークンは即時無効。
- 状態が `suspended` のエージェントからの接続は、トークン検証後に HTTP `403` で拒否する（`/mcp` および第3段階以降の `/mcp/admin`、第4段階の `/unread` 共通）。停止中のエージェント宛ての新しい質問は拒否し（監査ログの理由は `recipient_suspended`）、すでに受信箱にある項目は再開されるか7日で期限切れになるまで保持する。

### 3.6 暴走の防止（確定）

- エージェントごとに1日あたりの質問数上限を設ける。
- 未回答の質問は7日で期限切れにする。

## 4. 保存

| 項目 | 決定 | 状態 |
| --- | --- | --- |
| 保存先 | D1。メッセージと監査ログは別テーブル | 確定 |
| 許可ルールの正本 | D1。設定ファイルは初回デプロイ時の初期値投入にだけ使う | 確定 |
| メッセージ本文の削除 | 受け取りから24時間後（回答済み・期限切れが対象） | 確定 |
| 監査ログの内容 | 既定は本文なし。「誰が誰にどのカテゴリで聞き、結果がどうだったか」を残す | 確定 |
| 監査ログへの本文記録 | 設定で有効にできる。有効時も保存期間を区切る | 確定 |
| ルール変更の記録 | 誰が、いつ、何を、誰の承認で変えたかを残す | 確定 |
| 追加の暗号化 | しない（D1の保存時暗号化のみ） | 確定 |

## 5. 管理

### 5.1 画面（確定）

- 同じWorkerから配信する。
- Cloudflare Accessを前段に置き、ログイン処理はブリッジ側に持たない。一方でWorker側でもリクエストごとに `Cf-Access-Jwt-Assertion` のJWT署名（RS256）と `aud`・有効期限を検証し、Accessの設定漏れや `workers.dev` 直叩きで `/admin` が無防備にならないようフェイルクローズ（未設定時は503、検証失敗時は403）とする。
- ログイン元はGitHubを標準の選択肢として導入手順書に載せる。
- 機能：エージェント登録とトークン発行、監査ログ閲覧、停止・再開、ルール編集、カテゴリ編集、提案の承認・却下、管理者ボットの指名と権限スイッチ、呼び出し先URLの登録。
- 停止・再開：`suspended` 状態のエージェントは各接続窓口（`/mcp`、`/mcp/admin`、`/unread`）で HTTP `403` により拒否し、そのエージェント宛ての新規質問も遮断する（`recipient_suspended`）。既存の受信箱メッセージは再開または7日経過による期限切れまで保持する（3.5 節）。

### 5.2 人間だけができること（確定）

エージェントの登録・削除、トークンの発行・再発行、管理者ボットの指名替え、管理者ボットの権限スイッチの操作。

### 5.3 管理者ボット（確定）

- 同時に1体まで。指名は画面から利用者が行う。
- 質問したりされたりする参加者を兼ねる。ただし参加者用と管理者用で接続とトークンを分ける。

**通常の権限**

| 区分 | 操作 |
| --- | --- |
| 単独で即時実行 | エージェントの一時停止、許可の取り消し、質問数上限の引き下げ、監査ログ（本文なし）の閲覧 |
| 提案まで | 許可の追加、カテゴリの追加、上限の引き上げ、停止の解除 |
| 不可 | 5.2 節の操作、自分の権限設定の変更 |

- 提案は利用者が画面で承認して初めて反映される。
- 画面では、提案の理由文とは別に、承認すると何が変わるかをブリッジが機械的に生成して表示する。
- 未処理の提案は14日で却下扱いにする。同時に保留できる提案数に上限を設ける。

**任意の権限（どちらも画面からのみ切り替え、既定はオフ）**

| 権限 | 内容 | 条件 |
| --- | --- | --- |
| 本文閲覧 | 質問文・回答文を読める | 監査ログへの本文記録が有効なときだけ意味を持つ。本文は 3.3 節の枠に入れて渡し、読んだことを監査ログに残す。スイッチの横に注意書きを一文添える |
| 最高管理者権限 | 「提案まで」の操作を単独で実行できる | 有効期限付き（既定7日、無期限も選べる）。管理者ボット自身はオンにも延長にもできない |

- 最高管理者権限でもできないこと：トークンの発行・再発行、管理者の指名替え、自分の権限設定の変更、監査ログの停止・削除。
- 管理者ボットが行った変更はすべて記録し、画面（`/admin/adminbot`）から1操作で元に戻せる。
  - 一覧は `before_id` によるカーソルページ送りと「未取消のみ」「対象種別」での絞り込みを備え、100件を超える履歴や過去の未取消変更もすべてたどれる。
  - 同じ対象に管理者ボットの変更が重なっている場合は、最新の変更から指定した変更までを逆順に1操作でまとめて元に戻せる。途中で所有者の変更（`actor_type = 'owner'`）が挟まっている場合は、所有者の操作を上書きしないため自動取消を拒否する。
  - 説明文の却下（`description_rejected`）も取消対象に含み、対象エージェントが存在し新しい承認待ち説明文がない場合に限り、却下された説明文を承認待ちへ戻す。
- `/mcp/admin` の変更系ツール呼び出しには、直近1時間あたりの回数上限を設ける（既定60回/時、`ADMIN_BOT_HOURLY_MUTATION_LIMIT` で変更可能。`change_log` の `actor_type = 'admin_bot'` 件数で集計）。上限を超えた呼び出しは拒否し、`audit_log` に `admin_tool_denied`（理由 `admin_rate_limit_exceeded`）を記録する。読み取り専用ツール（`view_audit_log`、`list_proposals`、`list_pending_descriptions`）は上限の対象外とする。
- 本文閲覧と最高管理者権限を同時にオンにする瞬間だけ、画面で確認を1回挟む。

**把握しているリスク**: 管理者ボットは参加者を兼ねるため、参加者として受け取った質問文に仕込まれた指示で、管理者としての操作をさせられる可能性がある。最高管理者権限が有効なときは、これが全カテゴリの開示許可につながり得る。上の制限（有効期限、固定の禁止操作、変更回数の時間上限、1操作での巻き戻し、記録）はこの被害を限定するためのもの。

### 5.4 エージェントの説明文（確定）

- エージェント自身が専用ツールで提出する。長さに上限を設ける。
- 管理者ボットが承認するまで他のエージェントには見せず、以前の説明文を出し続ける。
- 管理者ボットが指名されていないとき、および管理者ボット自身の説明文は、利用者が画面で承認する。

## 6. 実装

- 言語はTypeScript。MCPの接続方式はStreamable HTTP。
- ライブラリは公式の `@modelcontextprotocol/server`（2.4.0）の `createMcpHandler`（Web Standard Fetch ベースの Streamable HTTP）と `zod`（4.6.7）を直接使い、Cloudflare の `agents` 補助パッケージは使わない（第1段階で採用・検証済み）。
- パッケージ管理、テスト、デプロイの道具はWorkersの標準的な構成に合わせる。

### 6.1 作る順番（確定）

| 段階 | 内容 |
| --- | --- |
| 1. 中核 | `ask`・`check_inbox`・`answer`・`list_agents`、ルール照合、質問数上限、期限切れ、監査ログ。登録とルール設定は初期値ファイルとコマンドで行う |
| 2. 画面 | Cloudflare Accessでの保護、エージェント登録とトークン発行、監査ログ閲覧、停止・再開、ルール編集 |
| 3. 管理者ボット | 締める操作、提案と承認、説明文の提出と監査、本文閲覧、最高管理者権限 |
| 4. 起こす仕組み | 呼び出し先URLへの新着通知、未読件数の窓口と件数確認トークン、定期確認のサンプルスクリプト |

第1段階の完了条件は、受入シナリオ（質問応答1往復）が「試験用MCPクライアント2つ」と「Muse＋試験用MCPクライアント1つ」で通ること。

### 6.2 対象エージェント

| 製品 | 扱い | 調査で分かったこと（2026-11-16 初期調査、2026-11-27 追記） |
| --- | --- | --- |
| Muse（Meta） | 最初の実機 | URLを貼る設定欄はなく、`credentials.request_api_access` でカスタムコネクタを作る。単一APIキーのヘッダー配置（`Authorization: Bearer` 相当）に対応し、接続先ホストは登録制。公式のインバウンドWebhook受信口とサイドチャットへの外部投稿APIはなく、ランタイム管理のcron（公式例 `5m`・`15m`・`1h`）とフック（最短5秒・既定60秒、`wake` でワーカー起動。資格情報は持てない）が常駐する。`Background sync` の Allow・Deny 行はユーザー作成のcron・フックの対象外（2026-11-27 実環境で確認）。Muse Mail（`@muse.ai`）もある |
| Grok Bot（xAI） | 2体目の実機 | Automation・Routine に公式の Webhook Trigger（`whsec_` 鍵の Standard Webhooks 署名）と定期実行がある。API・CLI は `Authorization` ヘッダー対応だが、`grok.com/connectors` UI は OAuth 前提の記述と食い違う。Webhook 起動ルーチンからプライベート Custom MCP を呼ぶ際のスコープ制限報告がある |

| instinct | 対象外 | 独自ツールを追加する手段がない（利用者が製品内で確認） |
| Claude Duet、Pickle | 未調査 | — |

## 8. 未確認の事実

実装時に確かめ、結果をこの文書に追記する。

- **確認済み**: 使用するライブラリのバージョンと対応状況（`@modelcontextprotocol/server` 2.4.0 の `createMcpHandler` による Web Standard Fetch Streamable HTTP と `zod` 4.6.7 を直接利用。Cloudflare の `agents` 補助パッケージは不要）。
- **確認済み（2026-11-27、Muse 実環境）**: Muse に公式のインバウンド Webhook とサイドチャット外部投稿 API はない。ランタイム管理の cron とフックはアプリ終了や VM 入れ替え後も常駐し、フックが `wake` を返すとワーカーエージェントが起動する。ただしフック自体はシークレットやコネクタ資格情報を持てない。`credentials.request_api_access` は単一 API キーのヘッダー配置に対応し、`Background sync` の Allow・Deny 行はユーザー作成の cron・フックには適用されない。
- **未確認**: Muse で実際に paab の `/mcp` へ Bearer 接続したとき、カスタム MCP ツールが権限ツリーと事前承認（preapproval）に対応して無人実行できるか。またフックから `GET /unread` 相当の外部 HTTP GET（低権限トークン付き）と `wake` 後のワーカーからのカスタム MCP 呼び出しが通るか（実機未試験。検証手順は [docs/agent-trigger-design.md](agent-trigger-design.md#5-第-4-段階実装前の実機検証ゲート)）。
- **未確認**: Grok Bot の `grok.com/connectors` UI でヘッダー方式が通るか（OAuth のみとする報告と食い違い）。また Webhook Trigger 起動のルーチンからプライベート Custom MCP を承認・スコープ制限なしで呼べるか（実機未試験）。
- **未確認**: Cue（Manus 2.0）で Automations の Webhook Trigger が Cue 個人エージェントの記憶と Custom MCP 接続を引き継いで動くか、別タスクになるか（実機未試験）。
- **未確認**: Grok Bot で VM とその上のスクリプトが会話の外でも動き続け、エージェント本体を起こせるか（実機未試験）。
- **未確認**: GitHubにパスキーでログインした場合にCloudflare Accessを通るか。拒否されたという未解決の報告が1件ある（https://community.cloudflare.com/t/zero-trust-access-github-oauth-with-username-pass-ok-but-not-passkey-for-same-acc/908415 ）。
